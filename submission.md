## Codebase map

Written during Milestone 1, before any bug investigation or code changes.

### Architecture at a glance

Mixtape is a Flask JSON API with a strict three-layer layout:

```
HTTP request -> routes/*.py (blueprint: parse input, format response, map errors)
            -> services/*.py (all business logic and DB queries)
            -> models.py (SQLAlchemy models + association tables)
```

`app.py` is an application factory (`create_app`) that configures a SQLite database (`mixtape.db` by default, overridable via `DATABASE_URL`), initializes the shared `db` object, and registers four blueprints under URL prefixes: `/songs`, `/playlists`, `/users`, `/feed`. There is no frontend; everything returns JSON.

### Files and what each one does

**`app.py`** - App factory and DB setup. The `db = SQLAlchemy()` object lives here and is imported by every model and service. It accepts a `config` dict override, which is how the tests swap in an in-memory SQLite DB. (The README warns against `python app.py` because the factory pattern plus direct execution double-imports the models.)

**`models.py`** - Six model classes and three plain association tables (no association model classes):

- `User` - has `listening_streak` (int) and `last_listened_at` (datetime) stored directly on the user row. Streaks are denormalized counters, not computed from events.
- `Song` - includes `shared_by` (FK to the user who shared it) and `shared_at`. Tags come through the `song_tags` association table with `lazy="subquery"`.
- `ListeningEvent` - one row per listen: `user_id`, `song_id`, `listened_at`. This is the raw data behind both the feed and (indirectly) streaks.
- `Rating` - `score` 1 to 5, with a **unique constraint on `(user_id, song_id)`**. One rating per user per song, so re-rating has to update, not insert.
- `Playlist` - has an `is_collaborative` flag; songs come through the `playlist_entries` table.
- `Notification` - `user_id` (recipient), `notification_type` (a string like `"song_added_to_playlist"`), `body`, `read` flag.

Association tables: `friendships` (symmetric many-to-many between users; the seed script inserts both directions explicitly), `song_tags`, and `playlist_entries`. The important one is `playlist_entries`: it is not just a join table, it carries a **`position` column** (explicit ordering, not insertion order) plus `added_by` and `added_at`. Playlist order is a first-class concept in the schema.

**`routes/songs.py`** - `/songs/search` (-> `search_service.search_songs`), `/songs/<id>` (-> `search_service.get_song`), `/songs/<id>/rate` POST (-> `notification_service.rate_song`), `/songs/<id>/listen` POST (-> `streak_service.record_listening_event`).

**`routes/playlists.py`** - create playlist and get metadata (-> `playlist_service`), `GET /playlists/<id>/songs` (-> `playlist_service.get_playlist_songs`), and `POST /playlists/<id>/songs` (-> `notification_service.add_to_playlist`; the notification service owns the add action, not the playlist service).

**`routes/users.py`** - user profile, `GET /users/<id>/streak` (-> `streak_service.get_streak`), notifications list and mark-as-read (-> `notification_service`). This is the only route file that touches the DB directly (one `db.session.get(User, ...)` for the profile endpoint).

**`routes/feed.py`** - `GET /feed/<user_id>/listening-now` (-> `feed_service.get_friends_listening_now`) and `GET /feed/<user_id>/activity` (-> `feed_service.get_activity_feed`).

**`services/streak_service.py`** - `record_listening_event` creates a `ListeningEvent` and calls `update_listening_streak(user, now)`, which compares calendar dates (`.date()`) between now and `user.last_listened_at`: same day means no change, a 1-day gap means increment, anything else resets to 1. It also re-attaches UTC to naive datetimes coming back from SQLite before comparing.

**`services/feed_service.py`** - `get_friends_listening_now` collects the user's friends' `ListeningEvent`s newer than a module-level `RECENT_THRESHOLD` cutoff, then deduplicates down to the single most recent event per friend. `get_activity_feed` is the unfiltered variant: the most recent N events regardless of age.

**`services/search_service.py`** - `search_songs` runs one query with an `outerjoin` to `song_tags` and a case-insensitive `ilike` filter on title/artist, then serializes through `Song.to_dict()` (which pulls tag names in).

**`services/notification_service.py`** - the generic `create_notification(user_id, type, body)` helper plus two action functions that live here rather than in domain services: `add_to_playlist` (appends the song to the playlist, then notifies the song's original sharer unless the sharer added it themselves) and `rate_song` (validates the score is 1 to 5, then upserts the `Rating` respecting the unique constraint). Also `get_notifications` and `mark_as_read`.

**`services/playlist_service.py`** - `create_playlist`, `get_playlist` (metadata only), `get_user_playlists`, and `get_playlist_songs`, which joins `Song` to `playlist_entries` and orders by the `position` column ascending.

**`seed_data.py`** - drops and recreates all tables, then seeds: 5 users with explicit bidirectional friendships, 10 tags, 13 songs deliberately split into 0-tag / 1-tag / 3-tag groups, listening events both recent (within 30 minutes) and old (up to 14 days), `last_listened_at` values for streak users, 3 playlists of 5 to 7 songs each with sequential `position` values, and one example `song_added_to_playlist` notification. The comments in the seed file say outright which data groups exercise which issues.

**`tests/`** - pytest suites for streaks, search, and playlists, each using the app factory with an in-memory SQLite DB. Baseline run **before any changes**: 10 passed, 3 failed (`test_streak_increments_on_sunday`, `test_playlist_returns_all_songs`, `test_playlist_returns_songs_in_order`). Recording that here so it's clear those failures are pre-existing and not something my changes caused.

### Data flow trace - a user rates a song

1. Client sends `POST /songs/<song_id>/rate` with JSON body `{"user_id": ..., "score": ...}`.
2. `routes/songs.py::rate()` validates that both fields are present (400 if not), coerces `score` to int, and calls `notification_service.rate_song(user_id, song_id, score)`.
3. `rate_song()` validates the score is 1 to 5, loads and existence-checks both the `Song` and the `User` (raising `ValueError`, which the route maps to a 400), then checks for an existing `Rating` for this `(user_id, song_id)` pair. Because of the unique constraint, an existing rating is updated in place; otherwise a new `Rating` row is inserted. It commits and returns the `Rating`.
4. The route serializes the rating with `to_dict()` and returns 201.

### Data flow trace - a friend adds your song to a playlist (the notification path)

1. Client sends `POST /playlists/<playlist_id>/songs` with `{"song_id": ..., "added_by": ...}`.
2. `routes/playlists.py::add_song()` delegates to `notification_service.add_to_playlist()`.
3. That function existence-checks song, adder, and playlist, appends the song to `playlist.songs` if it isn't already there, then calls `create_notification()` targeting the **original sharer** with type `"song_added_to_playlist"` - but only if `song.shared_by != added_by_user_id`.
4. The sharer later sees it via `GET /users/<id>/notifications`, which orders by `created_at` descending and can filter to unread.

### Patterns I noticed

- **Routes are thin, services are everything.** Every route parses input, calls exactly one service function, and translates `ValueError` into a 400/404. All queries and business rules live in `services/`.
- **Service boundaries follow the side effect, not the entity.** `rate_song` and `add_to_playlist` live in `notification_service.py`, presumably because those actions are supposed to generate notifications, while read-only playlist logic lives in `playlist_service.py`. So "which service owns this?" is answered by what the action triggers, not what table it touches.
- **Consistent error convention:** services raise `ValueError` with a human-readable message; routes catch it and pick the status code.
- **Denormalized counter plus raw event log:** streaks are a counter on `User`, but every listen is also recorded as a `ListeningEvent`. Two sources of truth, updated together in `record_listening_event`.
- **Timezone handling is deliberate:** everything is created as UTC-aware (`datetime.now(timezone.utc)`), and the streak service defensively re-attaches UTC to naive datetimes coming back from SQLite.
- **The seed data is issue-aware:** the seed script's comments flag which data subsets exist to exercise which open issues (multi-tag songs, recent vs old listening events).

One entry per fixed bug. Reproduction was done in Milestone 2, before any code changes; the remaining fields get filled in during Milestone 3 as each fix lands.

All reproductions were done on 2026-07-05 against a freshly seeded database (`python seed_data.py`), with the app running via `FLASK_APP=app:create_app flask run`. I reseeded afterward so the fix work starts from clean state. Baseline test suite before any changes: **10 passed, 3 failed** (`test_streak_increments_on_sunday`, `test_playlist_returns_all_songs`, `test_playlist_returns_songs_in_order`).

### Issue #1 - My listening streak keeps resetting

- **How I reproduced it:** Two ways. (1) Live through the API. The day I reproduced this, 2026-07-05, happened to be a **Sunday**, which turns out to be the trigger condition. Seed user `darius` has `listening_streak = 3` and `last_listened_at` set to yesterday (Saturday). `GET /users/<darius>/streak` returned `{"streak": 3}`. Then `POST /songs/<song_id>/listen` as darius - a consecutive-day listen that should push the streak to 4. `GET /users/<darius>/streak` afterward returned `{"streak": 1}`. The streak reset instead of incrementing. (2) The repo's own test `tests/test_streaks.py::test_streak_increments_on_sunday` (Saturday 2024-06-15 then Sunday 2024-06-16) fails out of the box with `assert 1 == 2`. On any other weekday the consecutive-day increment works (`test_streak_increments_on_consecutive_day` passes with Monday to Tuesday), so the bug is Sunday-specific.
- **How I found the root cause:** The call chain is `POST /songs/<id>/listen` in `routes/songs.py` -> `streak_service.record_listening_event()` -> `update_listening_streak(user, now)`. The first function just creates the `ListeningEvent` and delegates, so the streak decision lives entirely in `update_listening_streak()`. That function computes `days_since_last` from calendar dates and branches three ways: 0 days means no change, 1 day means increment, anything else resets to 1. The increment branch is where I stopped: `elif days_since_last == 1 and today.weekday() != 6:`. The docstring's rules mention nothing about weekdays, so a weekday condition bolted onto the increment branch was immediately suspect. Confirming what `weekday()` returns for Sunday (6) made it certain: on Sundays the increment branch is unreachable, and control falls through to the `else` that resets the streak. The failing test (`Saturday -> Sunday`, expected 2, got 1) matches that prediction exactly.
- **The root cause:** Python's `datetime.weekday()` returns 6 for Sunday. The increment branch in `update_listening_streak()` (`services/streak_service.py`) required `days_since_last == 1 and today.weekday() != 6`, so a consecutive-day listen was only rewarded if today was not a Sunday. Every Sunday listen with a Saturday listen behind it skipped the increment and hit the `else` branch, which sets `listening_streak = 1`. That is why users saw their streak "keep resetting": once a week, on Sunday, any active streak was wiped to 1 no matter how long it was. The `days_since_last` calendar math was never wrong; the extra weekday clause was the whole bug.
- **My fix and side-effect check:** One-line change in `services/streak_service.py`: the increment condition is now just `elif days_since_last == 1:`, deleting the `weekday() != 6` clause. The streak rules in the docstring (start at 1, no change same day, increment on consecutive day, reset after a gap) have no weekly component, so the clause had no legitimate purpose to preserve. Side-effect checks: the full suite now passes 13 of 13 (this was the last pre-existing failure). I verified both sides of the boundary in a REPL: Saturday -> Sunday increments (1 to 2), Sunday -> Monday increments (2 to 3), a second listen on the same Sunday is still a no-op, and skipping a day still resets to 1. I also re-ran the live Milestone 2 reproduction: darius (streak 3, last listened Saturday) listened on the real Sunday 2026-07-05 and his streak went to 4, where the identical request before the fix took it to 1.

### Issue #2 - Friends Listening Now shows people from yesterday

- **How I reproduced it:** The obvious check, `GET /feed/<nova>/listening-now`, showed nothing wrong, because all three of nova's friends have seeded listening events from 10 to 20 minutes ago and the feed deduplicates to each friend's most recent event. The bug only shows for a viewer whose friend's *most recent* listen is old. In the seed data that viewer is **kenji**: his friend nova's latest event is about 2 hours old, and his friend aaliya's is about 34 hours old. `GET /feed/<kenji>/listening-now` returned nova "listening now" to a song at `15:15` when the current time was around `17:23` - a 2-hour-old listen presented as happening right now. Aaliya's 34-hour-old event was excluded, which brackets the faulty cutoff somewhere between 2 and 34 hours. The seed comments say events within about 30 minutes are what should appear.
- **How I found the root cause:** The route (`/feed/<user_id>/listening-now` in `routes/feed.py`) delegates straight to `feed_service.get_friends_listening_now()`. Inside that function there are three candidate places a stale event could slip through: the cutoff computation, the query filter, or the per-friend dedup loop. The dedup loop only narrows results (most recent event per friend), so it can't add stale entries. The query filter is `ListeningEvent.listened_at >= cutoff`, which is the right comparison direction. That leaves the cutoff itself: `cutoff = datetime.now(timezone.utc) - RECENT_THRESHOLD`, and at the top of the file, `RECENT_THRESHOLD = timedelta(hours=24)`. A 24-hour window for a feature called "listening now" was the answer, and it matched the reproduction bracketing exactly: the 2-hour-old event (inside 24h) showed, the 34-hour-old event (outside 24h) didn't. The issue title "shows people from yesterday" is literally what a 24-hour window does.
- **The root cause:** The module-level constant `RECENT_THRESHOLD` in `services/feed_service.py` was `timedelta(hours=24)`. The query logic was correct - it filtered friends' `ListeningEvent`s to `listened_at >= now - RECENT_THRESHOLD` and deduplicated to the most recent per friend - but the window it was given was a full day, so anyone who listened at any point in the past 24 hours was presented as listening "now". Nothing conditional or subtle here once found: the mechanism is just a constant whose value contradicts the feature's meaning. The correct behavior requires a window measured in minutes, because the feature's claim to the user is about the present moment; the seed script documents the intended behavior directly ("Recent events (within the past 30 minutes) - should appear in 'listening now'" and the older events "should NOT appear in 'listening now' after fix").
- **My fix and side-effect check:** One-line change in `services/feed_service.py`: `RECENT_THRESHOLD = timedelta(minutes=30)`, matching the intent documented in the seed data. Side-effect checks: the constant is only read by `get_friends_listening_now`, but I specifically checked `get_activity_feed` in the same file because it's the adjacent feature most plausibly affected - its docstring says it is deliberately *not* recency-filtered, and it still returns all 8 old events after the fix (it never referenced the constant). Both sides of the new boundary verified live: kenji's feed is now empty (his friend nova's most recent listen is about 2 hours old), while nova's feed still shows all three of her friends whose listens are 10 to 20 minutes old. The full suite passes 15 of 15, including two new regression tests I wrote for this fix (see the regression test section below).

### Issue #3 - The same song keeps showing up twice in search

- **How I reproduced it:** This one required going below the API. `GET /songs/search?q=crown` (matching "Crown Heights Anthem", which has 3 tags) returned the song **once**, `count: 1` - the duplicate did not reproduce at the HTTP level in this environment. To check whether the underlying query was actually clean, I ran the equivalent raw SQL (`SELECT song.title FROM song LEFT OUTER JOIN song_tags ON song.id = song_tags.song_id WHERE ...`) against the same database: it returns **three identical rows** for that one song. The same statement built 2.0-style (`db.select(Song)` plus `.scalars().all()`) also returns 3 duplicate Song objects. The service happens to use the legacy `db.session.query(Song)` API, and in the installed SQLAlchemy (2.0.51) legacy `Query.all()` silently de-duplicates full-entity rows - so the query is genuinely wrong, but a library behavior hides it at the API layer. Control cases: a 1-tag song ("Block Party") and a 0-tag song ("Still Waters") each produce exactly one raw row, which confirms the duplication is conditional on a song having **2 or more tags** (each matching tag row multiplies the song in the join output).
- **How I found the root cause:** The route (`/songs/search` in `routes/songs.py`) just forwards the query string to `search_service.search_songs()` and counts the result, so the service query was the only candidate. The query reads: `db.session.query(Song).outerjoin(song_tags, Song.id == song_tags.c.song_id).filter(or_(title ilike, artist ilike))`. Two observations pinned it down. First, the filter never references the joined table - it only touches `Song.title` and `Song.artist` - so the join contributes nothing to *which* songs match. Second, the tags in the response don't come from the join either: `Song.to_dict()` reads the `tags` relationship, which loads through its own subquery. So the join's only actual effect is row multiplication: a LEFT JOIN produces one output row per matching `song_tags` row, meaning a 3-tag song becomes 3 rows, a 1-tag or 0-tag song stays 1 row. That is exactly the conditional behavior in the issue. The reason it doesn't show over HTTP in this environment is that the service uses the legacy `db.session.query()` API, and legacy `Query.all()` in SQLAlchemy 2.x silently de-duplicates full-entity rows; the modern `db.select(Song)` form of the identical query returns the 3 duplicates plainly. The reporter presumably hit a code path or library version without that safety net.
- **The root cause:** The `outerjoin` to `song_tags` in `search_songs()` (`services/search_service.py`) was dead weight that fanned out the result set. A LEFT JOIN returns one row per matched right-hand row, so every song appeared once per tag it had (minimum once). Nothing in the function needed the join: the WHERE clause filters on song columns only, and tag names are serialized through the ORM relationship, not the joined columns. The visible duplicates were conditional on a song having 2 or more tags because that is when the join produces more than one row, which is why users saw "the same song twice" only sometimes. In this exact environment SQLAlchemy's legacy Query masks the duplicates by uniquifying entities, but the query itself was wrong, and anything that bypasses that legacy behavior (the 2.0-style `select()` API, raw SQL, a count on the unde-duplicated rows) sees the duplicates.
- **My fix and side-effect check:** Removed the `.outerjoin(song_tags, ...)` line from the query in `services/search_service.py` (and the now-unused `song_tags` import). Deleting the join fixes the root cause directly: with no join there is no row fan-out to de-duplicate, at any layer, under any SQLAlchemy API. I chose this over adding `.distinct()`, which would have kept a useless join and hidden its symptom. Side-effect checks: all 13 tests pass, including the search suite. I compared the old and new query shapes through 2.0-style `select()` where nothing dedupes for you: old shape returns 3 rows for the 3-tag song, new shape returns 1. Searching by artist still works ("elara" returns the two distinct Elara Moon songs), 1-tag and 0-tag songs still return exactly one result each, tags still appear in the response (they come from the relationship, which the fix didn't touch), and a no-match query still returns an empty list.

### Issue #4 - Notified on playlist-add but not on rating

- **How I reproduced it:** Seed user simone shared "Crown Heights Anthem". `GET /users/<simone>/notifications` returned `count: 0`. Then nova rated simone's song: `POST /songs/<song_id>/rate` with `{"user_id": <nova>, "score": 5}` returned 201 with the saved rating. Simone's notifications afterward: still `count: 0`. No notification of any type was created for the rating. The working pattern to compare against exists in the same file and in the seed data: nova has a seeded `song_added_to_playlist` notification, produced by the code path that notifies a song's sharer when someone else adds it to a playlist. (Side finding, not one of the five issues: actually exercising `POST /playlists/<id>/songs` live returns a **500** - `playlist.songs.append()` can't populate the NOT NULL `position`/`added_by` columns on `playlist_entries`. Noting it here for honesty; the seeded notification is what demonstrates the intended working pattern.)
- **How I found the root cause:** The call chain is `POST /songs/<id>/rate` in `routes/songs.py` -> `notification_service.rate_song()`. The route only parses input and formats the response, so anything notification-shaped had to happen in the service. The productive move was comparing the two action functions that live side by side in `services/notification_service.py`. `add_to_playlist()` ends with a guarded call to `create_notification()`: if `song.shared_by != added_by_user_id`, notify the sharer. `rate_song()` has the same overall shape - existence checks, the write, `db.session.commit()` - and then just `return rating`. There is no wrong line to point at; the notification step is absent entirely. What made me confident this was the intended design rather than speculation is the architecture itself: rating a song has no business being in `notification_service.py` unless rating was supposed to trigger a notification, and `create_notification()`'s own docstring gives its example types as `'song_added_to_playlist' or 'song_rated'` - a `song_rated` type is named in the code but nothing ever created one.
- **The root cause:** `rate_song()` in `services/notification_service.py` was missing its notification step. The working feature and the broken one are parallel functions in the same file: both are "a friend interacted with your shared song" actions routed through the notification service. `add_to_playlist()` completes the pattern with a self-interaction guard plus `create_notification(...)` targeting `song.shared_by`; `rate_song()` stops after committing the rating. So ratings were being saved correctly (the 201 response proves that) while the sharer was never told, exactly matching the report "notified when a friend added my song to a playlist but not when they rated it". The cause is architectural in the sense the hints meant: not a wrong comparison or a typo, but an unfinished implementation of a two-function pattern, confirmed by the dangling `'song_rated'` type name in the docstring that nothing referenced.
- **My fix and side-effect check:** Added the missing block to `rate_song()` after the commit, mirroring `add_to_playlist()` line for line: if `song.shared_by != user_id`, call `create_notification()` with type `song_rated` and a body built the same way as the playlist one (`"nova rated your song 'Crown Heights Anthem' 5/5."`). Using the existing `create_notification()` helper and the type name already documented in `models.py` means no new pattern was invented. Side-effect checks: all 15 tests pass. Live checks: rating another user's song creates exactly one `song_rated` notification for the sharer; a user rating their *own* song creates none (the guard works, same as the playlist path); re-rating still updates the existing `Rating` row instead of violating the unique `(user_id, song_id)` constraint, since the fix didn't touch the upsert logic. One behavior worth stating openly: re-rating notifies again, which matches how the playlist function behaves (it also notifies on repeat adds), so the two paths stay consistent.

### Issue #5 - The last song in a playlist never shows up

- **How I reproduced it:** The seeded playlist "Late Night Vibes" has **7** rows in `playlist_entries` (I counted the association table directly). `GET /playlists/<id>/songs` returns `count: 6` - the six songs at positions 1 through 6, with the position-7 song ("Free Throws") missing. Also reproduced by the repo's own tests: `test_playlist_returns_all_songs` (expects 3, gets 2) and `test_playlist_returns_songs_in_order` fail out of the box.
- **How I found the root cause:** I started from the route: `GET /playlists/<id>/songs` in `routes/playlists.py` just calls `playlist_service.get_playlist_songs()` and returns whatever comes back, so the route couldn't be dropping anything. Inside `get_playlist_songs()` there are only two steps that could lose a song: the query itself or the return line. The query joins `Song` to `playlist_entries`, filters by playlist id, and orders by `position` ascending - nothing there limits the row count. The return line is `return [song.to_dict() for song in songs[:-1]]`. The `[:-1]` slice was the moment of certainty: it takes every element except the last one, and the symptom is exactly "the last song never shows up". The docstring even says "This function returns all songs in the playlist", so the intent and the code plainly disagree on one character sequence.
- **The root cause:** Python's `list[:-1]` slice returns a copy of the list with the final element removed. The query in `get_playlist_songs()` (`services/playlist_service.py`) correctly fetches all songs ordered by `position`, but the list comprehension iterated over `songs[:-1]` instead of `songs`, so the highest-position song was sliced off every response. Because the query is ordered ascending by position, the dropped element is always the most recently added song, which matches the user report. The failure scales down badly too: a playlist with exactly one song returned an empty list, since `[x][:-1]` is `[]`.
- **My fix and side-effect check:** One-line change in `services/playlist_service.py`: iterate over `songs` instead of `songs[:-1]`. This fixes the root cause directly because the query was already correct; only the serialization step was truncating it. Side-effect checks: the full test suite goes from 3 failures to 1 (both playlist tests now pass; the one remaining failure is the pre-existing Sunday streak test for Issue #1). All three seeded playlists now return 7 of 7 songs in position order. I also checked both sides of the boundary: an empty playlist still returns `[]`, and a one-song playlist now returns that one song where before the fix it returned nothing. Ordering is untouched since the fix didn't change the query.

## Regression test (stretch)

`tests/test_feed.py` contains two regression tests for the Issue #2 fix, written because the feed service had no test coverage at all (the shipped suites only cover streaks, search, and playlists).

- `test_listening_now_only_shows_recent_listens` seeds a viewer with two friends: one whose listening event is 10 minutes old and one whose event is 3 hours old. It asserts the recent friend appears in `get_friends_listening_now()` and the stale friend does not.
- `test_listening_now_empty_when_no_recent_listens` seeds a viewer whose only friend listened 3 hours ago and asserts the feed is empty.

Why these would have caught the bug: the buggy code used a 24-hour `RECENT_THRESHOLD`, so a 3-hour-old event passed the cutoff and the stale friend showed up in the feed. Both tests fail against that code - the first on `assert "stale" not in usernames`, the second on the feed not being empty. I verified this concretely rather than assuming it: I re-ran the tests with the threshold set back to `timedelta(hours=24)` in-process and both failed exactly as expected, then confirmed they pass against the fixed code. The 3-hour choice also guards the fix against quiet regression to any cutoff longer than 3 hours, not just a revert to 24.
